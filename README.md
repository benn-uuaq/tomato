# 토마토 수확 워크스페이스 (Elite CS616 + D435i + 다이나믹셀 그리퍼)

**한 대(Orin nano)에서 전부** 돌린다. 카메라·그리퍼는 Orin 에 USB 로, 로봇은 랜선으로
붙는다. 명령은 `./robot_run.sh` 하나다.

```
  ┌───────────────────────────── Orin nano ─────────────────────────────┐
  │ RealSense D435i ─► 한양대 통합 비전 노드 ─┐                           │
  │ 그리퍼 (USB, /set_pos) ◄──────────────────┼── 시퀀스 ─► 로봇 제어 ───┼──► Elite CS616
  │                                           │     ▲                     │   (29999/30001/502)
  │ 비전 패널  http://<Orin>:8081  (비전·그리퍼 켜기/끄기, 촬영 시험)    │
  │ 작업 UI    http://<Orin>:8080  (연결, [비전 시작], [작업 시작], 티칭) │
  └─────────────────────────────────────────────────────────────────────┘
```

## 실행

```bash
cd ~/tomato_ws && ./robot_run.sh
```

Orin 화면에 작업 UI 창(`http://localhost:8080`)이 뜬다. 다른 PC 브라우저에서는
`http://<Orin IP>:8080`.

1. **로봇 IP** 를 넣고 **[연결]**
2. **[비전 시작]** → "준비 완료 — 작업 UI 에서 [작업 시작] 하면 됩니다" (카메라·YOLO·그리퍼, 10~60 초)
3. 작업을 고른다 — **(•) 픽앤플레이스 / ( ) 무게 추정** (아래 "작업 종류")
4. **[작업 시작]** (픽앤플레이스는 [연속 시작] 도 된다)

끝낼 때는 터미널에서 Ctrl+C — 카메라·비전·그리퍼까지 함께 내린다.

| 옵션 | |
| --- | --- |
| `./robot_run.sh --connect` | 기억해 둔 로봇 주소(`~/.tomato_pick/connection.yaml`)로 바로 연결 |
| `./robot_run.sh --autostart` | 비전·그리퍼도 바로 켬 ([비전 시작] 을 누른 것처럼) |
| `./robot_run.sh --v1` / `--v3` | 비전 런치를 v1 / v3 로 (기본 v2 — README.odt 권장, 윤곽선 깊이로 반지름) |
| `./robot_run.sh --no-window` | 화면에 UI 창을 안 띄움 (SSH 로 실행하면 원래 안 띄운다) |
| `./robot_run.sh --restart` | 돌던 것을 내리고 다시 |
| `./stop.sh` | 전부 내림 — **한양대 터미널에서 켠 비전 노드도** 내린다 |
| `./vision_run.sh` | 비전만 (로봇 없이 비전 시험할 때) — 패널 창이 뜨고 비전·그리퍼를 바로 켬 |

`./run.sh` 는 `./robot_run.sh` 와 같다.

**한양대 쪽이 이미 켜 둔 노드는 그대로 쓴다** — 예를 들어 다른 터미널에서

```bash
cd ~/doosan_manipulator && source install/setup.bash
ros2 launch doosan_vision_grasp tomato_vision_d435i_v2.launch.py
ros2 run doosan_vision_grasp dyn_test
```

로 켜 두었으면 [비전 시작] 은 비전·그리퍼를 또 띄우지 않고 그것을 쓴다(같은 카메라·
시리얼 포트를 둘이 잡으면 둘 다 망가진다). 그쪽에서 켠 것은 이쪽에서 끄지 않는다.
이를 위해 ROS 는 **새 터미널과 같은 기본값**(ROS_DOMAIN_ID 0, 모든 인터페이스)을
쓴다. 한양대 터미널에서 ROS_DOMAIN_ID 를 바꿨다면 같게 맞춘다.

## 작업 UI

**UI 부터 뜨고, 로봇 연결은 화면에서 한다.** "연결" 카드에 **로봇 IP**(예:
192.168.1.200)를 넣고 **[연결]** 을 누르면 그때 붙는다. `--connect` 를 주면 이 버튼을
대신 누른다.

- 마지막에 연결한 주소는 `~/.tomato_pick/connection.yaml` 에 남아 다음에 미리 채워진다.
- 주소 형식이 틀리면(예: `192.168.1.2000`) 접속을 시도하지 않고 바로 알려 준다.
- 로봇이 아직 안 켜져 있어도 [연결] 을 누른 뒤에는 2 초마다 다시 시도한다.
  멈추려면 **[연결 해제]**. 연결되기 전에는 작업 시작을 거절한다.
- 맨 위 상태가 **"시퀀스 노드가 응답하지 않습니다"** 면 시퀀스 노드가 죽었거나 못 뜬 것이다
  (로봇 연결 표시는 로봇 노드에서 바로 받으므로 그대로 맞다). `robot_run.sh` 터미널의
  오류를 본다. 설정 파일 숫자는 `60` 이든 `60.0` 이든 받는다(2026-10-21 전에는 실수 자리에
  `60` 을 적으면 시퀀스 노드가 뜨지 못하고 로봇이 "끊김" 으로 보였다).

같은 카드 아래 **"비전"** 칸:

| 버튼 | 하는 일 |
| --- | --- |
| **[비전 시작]** | 비전 패널에 "전체 시작" — 카메라 + YOLO(한양대 런치), 그리퍼. 패널이 떠 있지 않으면 `vision_run.sh` 를 띄운다 |
| **[비전 정지]** | 비전 패널에 "전체 중지" — **패널이 켠 것만** 내린다. 작업 중(일시정지 포함)에는 거절 — 먼저 [정지] |
| 비전 패널 열기 | `:8081` 패널을 새 창으로 — 카메라 미리보기, 촬영 시험, 그리퍼 수동 열기/닫기 |

아래에 비전·그리퍼 상태(준비됨·켜는 중·꺼짐·문제 있음)가 1 초마다 보인다.

## 비전 패널 (:8081)

`robot_run.sh` 가 같이 띄우는 웹 화면이다(`vision_run.sh` 로 따로 띄워도 된다).

| 부품 | 패널이 띄우는 것 | "준비됨" 으로 보는 조건 | 패널에서 하는 일 |
| --- | --- | --- | --- |
| 비전 (카메라 + YOLO) | `tomato_vision_d435i_v2.launch.py` | 카메라 영상이 들어오고 비전 노드가 `/tomato/nearest_capture` 를 구독 | **촬영 시험(최근접)** + 결과 표, 카메라 미리보기 |
| 그리퍼 | `gripper_dynamixel_node` | 모터가 현재 위치를 답함 | **열기 / 닫기(작업 UI 에서 정한 값) / 위치 직접 입력(0~8000)** |

- 한양대 터미널에서 켠 노드는 **"패널 밖"** 으로 표시하고 그대로 쓴다. 한양대
  `dyn_test` 는 현재 위치를 내보내지 않아 "위치 피드백 없음" 으로 보인다.
- 준비 상태가 바뀔 때마다 터미널에도 `[상태] …` 한 줄이 찍힌다(화면 없이 쓸 때).
- 카메라 영상이 없으면 촬영 시험은 거절한다 — 비전 노드가 촬영 요청을 조용히
  무시해 결과가 영영 안 오기 때문이다.
- 그리퍼 노드는 한양대 `dxl_test`(2026-10) 처럼 **하드웨어 에러(과부하 등)를
  복구**한다 — 재부팅 → 토크 ON → 마지막 목표 재전송, 명령당 3 번까지. 자세한 것은
  아래 "그리퍼".
- 로봇이 작업하는 동안에는 촬영 시험·그리퍼 수동 조작을 하지 않는다.

모델은 `models/best.pt`(위치 인식) 와 `models/tomato_v1.pt`(무게) 다. 저장소에는
없으므로(용량) 따로 넣는다. 런치는 이 워크스페이스 → 한양대 워크스페이스
(`~/doosan_manipulator`) 순으로 파이썬·노드·모델을 찾는다.

## 비전 토픽

| 촬영 | 한양대 노드 결과 토픽 | 시퀀스에서 |
| --- | --- | --- |
| `nearest` — 가장 가까운 1 개 | `/tomato/nearest_position`, `/tomato/nearest_weight` | 3 단계 대기 자세에서 찾기 |
| `middle` — 화면 3x3 가운데 칸의 최근접 1 개 | `/tomato/middle_position`, `/tomato/middle_weight` | 카메라 중심 맞춘 뒤 재측정(이 무게를 씀) |
| `pick` — 전체, 가까운 순 | `/tomato/pick_positions`, `/tomato/pick_weights` | (쓰지 않음) |
| `capture` — 면적·높이 무게 | `/tomato/center_positions` …  `/tomato/heights` | (아래를 볼 때만 의미 — 쓰지 않음) |

어느 촬영을 쓸지는 `vision.first_capture` / `vision.recapture` (설정 파일).
카메라 좌표 → 로봇 좌표 변환은 시퀀스가 그 순간의 TCP 로 한다.

## 네트워크

| 장비 | 주소 | 설정 위치 |
| --- | --- | --- |
| Elite CS616 | 192.168.1.200 | 펜던트 |
| Orin (`enP8p1s0`, 유선) | 192.168.1.10 | `robot-lan` 프로필 (만들어 둠, 아래) |

로봇 주소가 다르면 UI 에 넣으면 된다(기본값은 `scripts/env.sh` 의 `ROBOT_IP`).

Orin 유선 주소는 아래 프로필로 고정해 두었다(재부팅해도 유지). `ip addr add`
로 붙인 주소는 NetworkManager 가 지워 버리므로 프로필이어야 한다.

```bash
sudo nmcli con add type ethernet ifname enP8p1s0 con-name robot-lan \
    ipv4.method manual ipv4.addresses 192.168.1.10/24 ipv4.never-default yes \
    ipv6.method ignore connection.autoconnect yes
```

## 준비 (한 번)

```bash
cd ~/tomato_ws && bash scripts/setup.sh
```

| 단계 | |
| --- | --- |
| ROS 노드용 의존 (`requirements/ros.txt`, 시스템 파이썬) | O |
| 가상환경 + YOLO 의존 | O — Jetson 이면 **torch 는 건드리지 않는다**(JetPack 휠) |
| `colcon build --symlink-install` | O |
| 폴더에 들어오면 자동 환경 | direnv 있으면 `.envrc` 승인, 없으면 `~/.bashrc` 훅 |
| 주변 확인 | 로봇 응답, 카메라 패키지, 시리얼 권한, 모델 파일 |

ROS 노드용 의존을 시스템 파이썬에 까는 이유: colcon 이 만든 ROS 실행 파일의
shebang 이 `/usr/bin/python3` 라서, 가상환경에만 깔면 `pyModbusTCP` 를 못 찾는다.

**업데이트**는 `git pull` 이다. 파이썬 코드만 바뀌면 그대로 반영되고(심볼릭 링크
빌드), 노드가 새로 생기거나 `setup.py` 가 바뀌었으면 한 번 다시 빌드한다.

```bash
cd ~/tomato_ws && git pull
PYTHONNOUSERSITE=1 colcon build --symlink-install    # 필요할 때만
```

`PYTHONNOUSERSITE=1` 은 꼭 붙인다 — Orin 의 `~/.local` 에 있는 새 setuptools 때문에
붙이지 않으면 심볼릭 링크 대신 복사로 빌드돼 코드 수정이 반영되지 않는다.

## 위치 가르치기

펜던트로 로봇을 원하는 자리에 세워 두고 작업 UI 버튼을 누르면 **지금
자세·관절값을 읽어 저장**한다(로봇은 움직이지 않는다). 저장 위치는
`~/.tomato_pick/taught_poses.yaml` 이며 설정 파일보다 우선한다. 작업 중에는
가르칠 수 없다(정지한 뒤에).

| UI 버튼 | 서비스 | 저장 |
| --- | --- | --- |
| 현재 위치 → 홈 자세 | `pick/teach/home_pose` | 관절 6 축 (1·10·15·16 단계) |
| 현재 위치 → 대기 자세 | `pick/teach/wait_pose` | TCP 6 축 **+ 관절 6 축** (2 단계는 관절값으로 movej) |
| 현재 위치 → 놓는 자리 | `pick/teach/place_pose` | TCP 6 축 + 관절 6 축 |
| 현재 위치 → 하강 한계 | `pick/teach/descend_limit` | TCP 6 축 — **그 베이스 Z 가 하강 한계** (아래 "하강 한계") |
| ★ 홈 ↔ 대기 경유점 추가 / 마지막 지우기 / 모두 지우기 | `pick/teach/waypoint_wait_{add,undo,clear}` | 관절 6 축을 목록 끝에 |
| ★ 홈 ↔ 놓는 자리 경유점 추가 / … | `pick/teach/waypoint_place_{add,undo,clear}` | 〃 |
| 놓기 높이 [저장] | (파라미터) | 접근 높이·여는 높이 mm |
| 가르친 값 모두 지우기 | `pick/teach/clear` | 설정 파일 값으로 복귀 |

**경유점**은 홈에서 나가는 순서로 쌓는다. 홈 → 대기 길에는 그 순서로, 대기
쪽 → 홈 길에는 거꾸로 거친다(놓는 자리도 같다). 장애물을 피해 가는 자세를
펜던트로 하나씩 만들어 [경유점 추가] 를 누르면 되고 코드는 고칠 필요가 없다.
코드에서 구간을 고르는 곳은 `pick_sequence_node.py` 의 `★ 경유점` 표시다.

예전 파일(대기·놓는 자리 자세만 있는 것)도 그대로 읽는다. 다만 **홈은 새로
가르쳐야** 시작할 수 있고, 대기 자세 관절값이 없으면 로봇이 자세로 역기구학을
풀어 간다 — 대기 자세를 한 번 다시 가르치면 관절값까지 저장된다. 예전에 숫자로
넣던 `max_descend_z_mm` 는 읽지 않는다 — 하강 한계는 새로 가르친다.

### 하강 한계

펜던트로 로봇을 "이보다 아래로는 가면 안 되는" 높이에 세우고 **[현재 위치 → 하강
한계]** 를 누른다. 그 자세의 **베이스 Z** 가 한계가 된다.

- **가르치기 전에는 작업 시작을 거절한다**(홈과 같다).
- 토마토 쪽으로 직선으로 다가가는 **4 (중심 맞춤)·6 (파지점 정렬)·7 (하강)** 단계는
  움직이기 전에 목표 Z 를 본다. 한계보다 아래면 **움직이지 않고 멈춘다**
  ("7. 하강: 목표 Z 190.0 mm 가 하강 한계 Z 200.0 mm 보다 낮아 움직이지 않습니다").
  한계까지 깎아서 내려가 집지는 않는다 — 엉뚱한 높이에서 그리퍼를 닫지 않게.
- 직선 이동이라 끝점이 한계 위면 가는 길 전체가 한계 위다. 그래도 움직이는 중에
  실제 TCP Z 가 한계보다 2 mm 넘게 내려가면 바로 세운다(이중 안전).
- 놓기(11~14)·관절 이동(홈·대기·경유점)은 이 한계를 보지 않는다 — 가르친 자리로 가는
  이동이고, 상자가 픽 쪽 한계보다 낮을 수 있기 때문이다.
- **TCP 가 벽을 보면** 7 단계 하강은 수평이라 베이스 Z 한계가 깊이를 막지 못한다.
  깊이를 잘못 쟀을 때가 걱정되면 `descend.max_travel_mm`(하강 거리 한도, 기본 0 = 끔)
  를 준다.

## 그리퍼

작업 UI 의 **[그리퍼]** 칸에서 정하고 [저장] 한다(`~/.tomato_pick/taught_poses.yaml`,
설정 파일보다 우선). 비전 패널의 [열기]/[닫기] 버튼도 같은 값을 쓴다.

| 칸 | 쓰는 곳 | 처음 값 |
| --- | --- | --- |
| 닫기 위치 (집기) | 8 단계 | 6000 |
| 열기 위치 | 13 단계 | 0 |
| 닫는 동안 기다림 (초) | 8 단계 뒤 9 상승 전까지 | 1.5 |
| 여는 동안 기다림 (초) | 13 단계 뒤 14 상승 전까지 | 1.5 |

- 위치는 **0 ~ 8000** (4095 가 모터 한 바퀴). 넘는 값은 UI·패널·그리퍼 노드가 모두
  거절한다. 상한을 바꾸려면 `tomato_pick.yaml` 의 세 곳(`gripper.max_position`,
  `/gripper_dynamixel.max_position`, `/tomato_vision_panel.gripper_max_position`)을 같게.
- 직접 움직여 맞춰 보려면 비전 패널의 [그리퍼] 칸 → 위치 입력 → [이동]. 맞는 값을 찾으면
  작업 UI 에 적고 [저장].
- 한 바퀴를 넘기 때문에 그리퍼 노드는 시작할 때 모터를 **확장 위치 모드(4)** 로 두고,
  프로파일 속도 150 · 가속도 50 을 쓴다(재부팅하면 지워지는 값이라 복구 때마다 다시 쓴다).
- **바퀴 수 보정**: 모터는 재부팅·전원 재투입 때 몇 바퀴째였는지 잊고 위치를 0~4095 로
  다시 센다. 과부하로 재부팅 복구를 하거나 전원을 껐다 켠 뒤 그대로 6000 을 보내면 **한
  바퀴 더 조인다.** 그래서 그리퍼 노드가 직전 위치(복구 때) / 파일에 남긴 마지막 위치
  (`~/.tomato_pick/gripper_state.txt`, 켤 때)와 비교해 잃은 바퀴 수를 되찾는다. 켤 때
  위치가 마지막 위치와 바퀴 수만이 아니라 다르면(손이나 다른 프로그램으로 움직였으면)
  보정하지 않고 경고만 남긴다 — **그리퍼를 연 상태로 끄고 켜는 게 가장 안전하다.**
- 한양대 `dyn_test`(Orin 의 `dxl_test.py`, 확장 위치판)를 대신 켜 두면 패널은 그것을
  그대로 쓴다. 그때는 위 보정이 없다.

## 외부 시스템과 작업 트리거 주고받기

작업 시작·상태는 ROS 토픽·서비스로도 주고받을 수 있다(같은 ROS 도메인에서).

| 방향 | 이름 | 타입 | 내용 |
| --- | --- | --- | --- |
| 외부 → 로봇 | `pick/trigger` | `std_msgs/Empty` | 한 사이클 시작 |
| 외부 → 로봇 | `pick/command` | `std_msgs/String` | `start` / `loop` / `stop` / `pause` / `resume` |
| 외부 → 로봇 | `pick/start`, `pick/start_loop`, `pick/stop`, `pick/pause`, `pick/resume` | `std_srvs/Trigger` | 같은 명령을 서비스로 (성공 여부를 돌려받는다) |
| 로봇 → 외부 | `pick/status` | `std_msgs/String` | 현재 단계·좌표·무게·오차·미설정 항목 (JSON, 5 Hz) |
| 로봇 → 외부 | `pick/result` | `std_msgs/String` | 사이클 종료 결과 (성공 여부·무게·높이) |
| 로봇 → 외부 | `pick/done` | `std_msgs/Bool` | 사이클 종료 신호 하나만 필요할 때 |
| 로봇 → 비전 | `/tomato/nearest_capture`, `/tomato/middle_capture` | `std_msgs/Empty` | 촬영 트리거 (약 1.5 초 측정) |
| 비전 → 로봇 | `/tomato/nearest_position`, `/tomato/middle_position` | `geometry_msgs/PoseArray` | 토마토 위치 **m**, 카메라 optical frame, Z 는 앞면 |
| 비전 → 로봇 | `/tomato/nearest_weight`, `/tomato/middle_weight` | `std_msgs/Float32MultiArray` | 무게 **g** (구체 근사) |
| 로봇 → 그리퍼 | `/set_pos` | `std_msgs/Int32` | 다이나믹셀 목표 위치 (작업 UI 의 닫기·열기 값, 0~8000) |

세 개의 비전 토픽은 **같은 순서**로 한 번씩 발행된다(i 번째 pose 와 i 번째
무게가 같은 토마토다). 검출이 0 개여도 빈 목록이 오므로 로봇이 매달리지
않는다.

명령줄에서 걸어 보려면:

```bash
ros2 topic pub --once /pick/trigger std_msgs/msg/Empty "{}"
ros2 topic pub --once /pick/command std_msgs/msg/String "{data: 'loop'}"
ros2 topic echo /pick/result
```

## 작업 종류

작업 UI 의 [작업 시작] 위에서 고른다(브라우저마다 마지막 선택을 기억한다).

| 작업 | 하는 일 | 미리 가르칠 것 |
| --- | --- | --- |
| **픽앤플레이스** | 아래 "작업 순서" 1~16 단계 | 홈 · 대기 자세 · 놓는 자리 · 하강 한계 |
| **무게 추정** | 토마토 앞에서 카메라 중심을 맞추고 무게만 잰다(집지 않음) | 홈 · 대기 자세 |

**무게 추정** 순서

| 단계 | |
| --- | --- |
| 1 홈 → 2 대기 자세 | 픽앤플레이스와 같다 (★경유점) |
| 3 촬영 → 4 카메라 중심 맞춤 | 최근접 촬영 → 중심으로 이동 → **중앙 재측정**(`/tomato/middle_capture`) (픽앤플레이스 3·4 와 같다) |
| 5 무게 확인 | **팝업**에 중앙 재측정의 무게(구체 근사, 크게)·지름·위치. 로봇은 그 자리에서 기다린다 |
| → **[완료 (홈으로)]** | ★경유점을 거꾸로 거쳐 홈 → 끝 (`pick/result` 에 무게) |
| → **[다시 촬영]** | 홈 → 2 대기 → 3 촬영 → 4 중심 → 5 → 6 팝업 다시 |

- 토마토를 못 찾았거나(대기 자세·재측정·무게 촬영) 결과가 늦으면 멈추지 않고 팝업에
  "결과 없음" 과 이유를 띄운다 — 토마토 위치를 바꾸고 [다시 촬영] 하면 된다.
- 무게는 **중심을 맞춘 뒤의 중앙 재측정 값을 그대로** 쓴다(`vision.weight_capture: recapture`).
  화면 가운데 칸의 바로 그 토마토라 따로 촬영하지 않는다. 한양대 무게 추정 촬영
  (`/tomato/capture`, 면적·높이)은 옆 토마토의 무게가 나온 적이 있어(2026-10-21) 쓰지 않는다
  — 다시 쓰려면 `weight_capture: weight`.
- 팝업 버튼은 서비스 `pick/weight/done`, `pick/weight/retry` 다(`pick/command` 의
  `weight` / `weight_done` / `weight_retry` 로도 된다). 무게 추정 시작은 `pick/start_weight`.

## 작업 순서 (픽앤플레이스)

현장에서는 토마토를 **벽면 쪽으로** 따야 해서 TCP 가 아래가 아니라 벽을 본다.
그래서 픽 쪽 이동은 모두 **TCP 기준**이고, 장애물이 많은 홈 ↔ 대기 / 홈 ↔ 놓는
자리 구간은 **관절 이동 + 경유점**으로 간다.

| 단계 | 이동 | 기준 |
| --- | --- | --- |
| 1 홈 | movej | 가르친 관절값 |
| 2 대기 자세 | movej, ★경유점 순서대로 | 가르친 관절값 (없으면 자세 → 역기구학) |
| 3 촬영 → 좌표 수신 | — | **최근접 촬영**(`nearest`) — 가장 가까운 1 개 |
| 4 카메라 중심을 토마토에 맞춤 → 다시 촬영 | movel | **TCP x·y 평면** (벽까지 거리 그대로) → **중앙 재측정**(`middle`) |
| 5 크기·무게 확인 | — | 중앙 재측정 무게(구체 근사) |
| 6 그리퍼 파지점 정렬 | movel | **TCP 기준** 카메라→그리퍼 오프셋 |
| 7 하강 | movel | **TCP +z**, 거리는 카메라 깊이로 계산 — **가르친 하강 한계 Z 아래로는 안 감** |
| 8 그리퍼 오므리기 | — | `/set_pos` **닫기 위치**(작업 UI, 처음 값 6000) → 닫는 동안 기다림 |
| 9 상승 | movel | **TCP -z**, 6 단계 자세로 = 대기 자세와 같은 선상 |
| 10 홈 | movej, ★경유점 거꾸로 | |
| 11 놓을 자리 위로 | movej, ★경유점 순서대로 | 놓는 자리 + **접근 높이(UI 에서 지정)**, 베이스 Z |
| 12 감속 하강 | movel | 여는 높이까지 (베이스 Z, 상자 위) |
| 13 그리퍼 열기 | — | `/set_pos` **열기 위치**(처음 값 0) → 여는 동안 기다림 |
| 14 상승 | movel | 접근 높이로 |
| 15 홈 | movej, ★경유점 거꾸로 | **연속 운전이면 여기서 2 (대기 자세) 로** |
| 16 작업 끝 — 홈 | (15 에서 왔으면 이미 홈 — 움직이지 않음) | ★ 완료 신호 자리(추후 지정) |

- 예전의 "16 대기 자세로 갔다가 17 홈" 은 없앴다 — 한 개만 옮길 때 홈 → 대기 → 홈
  을 헛걸음했기 때문이다.
- **토마토가 없으면** 오류가 아니라 작업 끝이다 — 16 단계로 홈에 가서(대기 자세에서
  ★경유점을 거꾸로 거쳐) "토마토
  N 개를 옮기고 더 없어 마쳤습니다" 로 끝난다(연속 운전의 정상 종료).
- **하강 거리** = 토마토 앞면 깊이 + 33 (플랜지→카메라 앞면) − 172 (플랜지→핑거 끝)
  + **47.5** (더 들어갈 양). 한양대 실측 5 회(gripper_moving_test, v2 test)에서 늘
  "깊이 − 91.5 mm" 를 내려 집었고 이 식이 그 값을 그대로 낸다(깊이 303.4 → 211.9 mm).
  모두 `descend.*` 설정. 높이 제한은 거리가 아니라 **가르친 하강 한계**(위)로 한다.
- **중앙 재측정에서 토마토가 안 잡히면**(가운데 칸 밖이거나 놓침) 엉뚱한 토마토를
  집지 않게 멈춘다. 대기 자세 첫 촬영에서 없으면 작업 끝이다.
- **목표는 절대 자세로 한 번만 계산**한다. 하강 도중 일시정지했다 재개해도 두
  배로 들어가지 않는다(시뮬레이터로 확인).
- 놓기(11~14)는 상자 위에서 내려놓으므로 **베이스 Z** 기준이다.

## 현장에서 확인할 것 (벽을 보는 자세로 바꾼 뒤)

| 항목 | 왜 | 확인 방법 |
| --- | --- | --- |
| **회전 표기** `orientation_format` (기본 `rpy`) | TCP 기준 이동은 로봇이 보고한 회전으로 방향을 계산한다. 틀리면 엉뚱한 방향을 목표로 잡는다(도착 판정에 걸려 멈추긴 한다) | `python3 src/elite_robot_controller/tools/check_pose_convention.py 192.168.1.200` — **로봇을 움직이지 않고** DH 정기구학으로 비교 |
| **카메라 → TCP 축 대응** `vision.camera_axis_map` | 기본 `["-y","-x"]` 는 두산·아래 보기·베이스 기준 측정값이다 | 틀리면 두 번째 촬영에서 오차가 줄지 않아 **시퀀스가 스스로 멈춘다**("오차가 72 → 72 mm"). 그때 부호·축을 바꾼다 |
| **카메라 → 그리퍼 오프셋** `gripper.tcp_offset_mm` (TCP 기준) | 기본 `[100, 32.5, 0]` 도 두산·베이스 기준 | 중심 맞춘 뒤 6 단계에서 그리퍼가 토마토 앞에 서는지 저속으로 본다 |
| **더 들어갈 양** `descend.grasp_depth_mm` (47.5) | 한양대(두산) 실측 기준. 로봇 TCP 를 플랜지로 둔 경우의 값이다 | CS616 의 TCP 설정이 다르면(그리퍼 길이를 TCP 에 넣었으면) 다시 맞춘다 |
| **로봇 전원·원격 모드** | 팔 전원이 꺼져 있으면 컨트롤러가 30001 을 열지 않아 연결이 안 된다(2026-10-16 확인: POWER_OFF, LOCAL) | 펜던트에서 전원 켜고 브레이크 해제. 이동이 안 먹으면 원격 모드도 켠다 |
| 11 단계 놓을 자리 위 | 관절값이 아니라 자세로 가서 로봇이 역기구학을 푼다(지금 관절값에 가까운 해) | 자세가 이상하게 뒤집히면 놓는 쪽 경유점을 놓는 자리 가까이에 하나 더 |

안전장치: 카메라 중심 이동이 100 mm 를 넘으면 거절(`align_max_step_mm`), 두 번째
촬영 오차가 첫 오차의 70 % 를 넘으면 멈춤(`axis_check_ratio`), 4·6·7 단계는 가르친
하강 한계 Z 아래로 안 감, 경유점마다 섬(`waypoint_blend_m: 0`). 하강 거리 한도
(`descend.max_travel_mm`)는 기본으로 꺼져 있다.

참고(README.odt): 끝단 중심에서 **카메라**는 정면 100.045 mm / 하단 8 mm,
카메라 두께 25 mm → 33 mm, 화면 중심은 오른쪽으로 17.5 mm. **그리퍼**는
하단으로 102 mm(핑거 제외) / 172 mm(핑거 전개 후 끝단).

python3 src/elite_robot_controller/tools/elite_robot_simulator.py &

서로를 못 보게 하고 TCP 브리지로만 잇는다.

# "Orin" 쪽 (도메인 31): 브리지 서버 + 가짜 YOLO/그리퍼
ROS_DOMAIN_ID=31 ROS_LOCALHOST_ONLY=1 ros2 run doosan_vision_grasp tomato_tcp_bridge &
ROS_DOMAIN_ID=31 ROS_LOCALHOST_ONLY=1 python3 <가짜 비전 노드> &

# 로봇 시뮬레이터
python3 src/elite_robot_controller/tools/elite_robot_simulator.py &

ROS_DOMAIN_ID=32 VISION_HOST=127.0.0.1 ROBOT_IP=127.0.0.1 \

## 두 대로 나눠 쓸 때 (예전 방식)

비전은 Orin, 로봇·UI 는 다른 PC(WSL 등)에 두고 TCP 브리지(포트 9000)로 잇는 구성도
남아 있다. 역할을 직접 고를 때만 이렇게 동작한다.

```bash
./run.sh --role orin --autostart      # Orin: 비전 패널 + 브리지 서버
./run.sh --role pc                    # 로봇 PC: 로봇·UI + 브리지 클라이언트 (Orin IP 칸이 생김)
```

- 로봇 PC 쪽 ROS 는 다른 장비를 보지 않는다(`ROS_LOCALHOST_ONLY=1`, 도메인 7) — 같은
  토픽이 양쪽에서 보이면 명령이 메아리처럼 되돌아오기 때문이다. 둘을 잇는 건 브리지뿐이다.
- 브리지(JSON Lines, protocol 3): 로봇 PC → Orin 은 촬영 명령(`nearest_capture` 등)·그리퍼
  위치·ping, Orin → 로봇 PC 는 촬영 결과(카메라 좌표). 결과는 로봇 PC 에서 같은 토픽
  이름으로 다시 나온다. 작업 중 끊기면 시퀀스가 로봇을 세운다.
- 로봇 PC UI 의 [비전 시작] 은 Orin 패널을 HTTP 로 부르고, 패널이 없으면 SSH(**키 인증만**,
  `ssh-copy-id nano@<Orin IP>` 한 번)로 Orin 의 `vision_run.sh` 를 띄운다. Orin 계정·폴더는
  `ORIN_USER` / `ORIN_WS`(기본 `nano` / `~/tomato_ws`).
- 로봇 PC(WSL) 준비는 `TOMATO_ROLE=pc bash scripts/setup.sh` — 가상환경·torch 를 깔지 않는다.
